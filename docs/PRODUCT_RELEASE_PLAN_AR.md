# خطة تحويل NetRewind إلى منتج سطح مكتب موثوق

> **حالة الوثيقة:** خطة تنفيذ، وليست وصفًا للميزات المتاحة حاليًا.
> **المبدأ الحاكم:** لا يدّعي المنتج معرفة ما لا يملك عليه دليلًا.
>
> **حالة التنفيذ:** يسجّل `CHANGELOG.md` ما أُنجز فعليًا، وتوجد أدلة الاختبار
> في `docs/evidence/` وفهرسها في `docs/testing.md`. يبقى هذا المستند مرجعًا
> للخطة الأصلية، ويُقاس التقدم بالأدلة القابلة للتحقق لا بتعديل بنود الخطة.

## 1. القرار التنفيذي

يتكوّن NetRewind من جزأين محليين مستقلين بوضوح:

1. **وكيل التسجيل** (`netrewind-agent`) يعمل بأقل الصلاحيات اللازمة، ويرصد
   التغيّرات ويحفظ الأدلة.
2. **تطبيق سطح المكتب** (`NetRewind Desktop`) يعمل بصلاحيات مستخدم عادي، ويقرأ
   الأدلة ويشرح الحوادث ويدير إعدادات الوكيل. ولا يملك صلاحية تغيير الشبكة.

يبدأ الإصدار التجاري بقدرات متطابقة لقراءة الأدلة وتحليلها على Windows وLinux.
بعد ذلك يُضاف تكافؤ موثق في الرصد الحي ضمن حدود كل منصة. ولا تُوصف أي قدرة بأنها
مدعومة لمجرد نجاح فتح التطبيق؛ إذ تعرض الواجهة القدرات الفعلية ومصدر كل دليل.

لا يبدأ العمل على الذكاء الاصطناعي قبل استقرار مسار الأدلة ومحرّك القواعد
والواجهة واختبارات المنصتين. ويعمل الذكاء المحلي كطبقة **شرح واقتراح مقيدة
بالدليل** فوق المحرّك الحتمي، لا بديلًا عنه ولا أداة تدير الشبكة ذاتيًا.

## 2. ما هو موجود الآن — نقطة البداية التي يجب عدم هدمها

يمتلك المشروع نواة متينة مكتوبة بلغة Go، لكنه لم يكن عند كتابة الخطة تطبيق سطح مكتب مكتملًا:

| موجود ومثبت | المصدر في الشجرة | أثره في الخطة |
|---|---|---|
| بنية أحداث ذات إصدارات، ودليل مرفق بكل حدث، وساعة فعلية وأخرى رتيبة، وهوية زمنية | `internal/event`, `internal/identity`, `docs/schema.md` | تظل عقد البيانات المشترك بين المنصتين وطبقة الذكاء الاصطناعي. ويتطلب أي تغيير ترحيلًا ونموذج اختبار متوافقًا مع الإصدارات السابقة. |
| SQLite، وسياسة احتفاظ، وتجميع للتكرارات، وأحداث لفجوات الرصد أو الإسقاط | `internal/store`, `cmd/netrewindd` | يمثّل سجل الأدلة المحلي، وليس ذاكرة تخزين مؤقتة للواجهة. |
| محرك Isnad وقواعد YAML تفرّق `causes` و`correlates` و`precedes` | `internal/correlate`, `rules/` | هو خط الأساس الحتمي الذي تُقاس عليه اقتراحات الذكاء. |
| أداة سطر أوامر وواجهة ويب للقراءة فقط، تعملان محليًا افتراضيًا، وقوالب لا تعتمد على JavaScript | `cmd/netrewind`, `internal/web` | تُستعملان مرجعًا للسلوك ومصدرًا أوليًا لبيانات الواجهة الجديدة، وليستا واجهة برمجية مكتملة. |
| الرصد الحي على Linux عبر netlink وeBPF وnftables ومقبس الحزم والمجسّات | `internal/collect/*_linux.go` | هذا هو منتج Linux الحالي. يجب فصل الدلالة عن تفاصيل نظام التشغيل قبل إضافة Windows. |
| حزم Linux وخدمة systemd وصورة حاوية وصورة جهاز وتحديث موقّع | `deploy/`, `internal/update` | لا يُستبدل مسار الثقة القائم، بل يُعمم بحذر على تطبيق سطح المكتب. |

اجتازت الأوامر `go test ./...` و`go vet ./...` و`GOOS=linux go vet ./...`
التحقق على Windows. وتوثّق `docs/evidence/DEMONSTRATION.md` اختبارات سابقة على
Linux، منها اختبار السباق ونجاح 14 من 14 سيناريو لحقن الأعطال وصفحات الويب
والمقاييس. تعذر تشغيل `go test -race` محليًا في هذه الجلسة لأن البيئة تستخدم
`CGO_ENABLED=0`. ولا يُعد ذلك نجاحًا أو فشلًا للشيفرة؛ لذلك يبقى اختبار السباق
إلزاميًا في بيئة تتوفر فيها أدوات بناء لغة C، كما هو الحال في نظام التكامل المستمر على Linux.

### الفجوات التي تمنع وصف المشروع الحالي بأنه برنامج Windows/Linux متكامل

- المجمّعات خارج Linux كانت وحدات بديلة تعيد `ErrUnsupported`. كان بناء
  `netrewindd.exe` ممكنًا، لكن الرصد الحي يتوقف ويسجّل `system.collector_down`.
- كانت واجهة الويب للقراءة فقط، بلا واجهة برمجية موثقة أو مصادقة، لأنها مرتبطة
  بواجهة الحلقة المحلية (`loopback`).
  ولا يجوز كشفها على الشبكة أو استخدامها كما هي كخلفية لتطبيق تجاري.
- لم تكن هناك خدمة Windows أو واجهة إعداد أو معالج صلاحيات أو حزمة MSI/MSIX/NSIS
  موقّعة أو سياسة تثبيت وإزالة واسترجاع خاصة بـWindows.
- كان مخطط الأحداث واسعًا، لكنه يحتاج إلى نموذج قدرات وإصدارات للواجهة البرمجية وأداة لاختبار
  الترحيلات قبل دعم عملاء متعددين.
- لم تتوفر مجموعة بيانات واقعية موسومة أو مقاييس جودة أو سياسة للنماذج، ولذلك لم
  يكن من المقبول الادعاء بأن النموذج يعرف سبب العطل.

## 3. نطاق المنتج والإصدارات

### 3.1 الإصداران المطلوبان

| الإصدار | ما يسلمه للمستخدم | حزمة الإصدار |
|---|---|---|
| **Windows x64** | تطبيق سطح المكتب مع خدمة تسجيل اختيارية، واستيراد حزم الأدلة، والتحليل المحلي، وصفحة القدرات، وإعدادات واضحة، وذكاء اصطناعي اختياري بعد اجتياز بوابة الجودة | مثبّت موقّع بصيغة `.exe` أو NSIS للمستخدمين و`.msi` للمؤسسات. ولا تحذف إزالة التثبيت الأدلة إلا بخيار منفصل وواضح |
| **Linux x86_64** | تطبيق سطح المكتب مع خدمة تسجيل مبنية على الوكيل الحالي ويديرها systemd، إضافة إلى تحليل الأدلة والرصد الحي | حزم `.deb` و`.rpm` للخدمة والتطبيق، وAppImage للعارض عند الحاجة. ثم يُضاف Linux arm64 بعد اجتياز الاختبارات نفسها |

لا يُضمّن ملف النموذج في المثبّت؛ فحجمه وترخيصه وآلية تحديثه تختلف عن البرنامج.
ويُنزّل في خطوة مستقلة بعد شاشة موافقة تعرض الاسم والإصدار والحجم والرخصة وبصمة التحقق.

### 3.2 تعريف النسخة الأولى الصادقة

**مشترك بين النظامين:** صحة المسجّل وفجوات الرصد والحوادث والخط الزمني والبحث
حسب المضيف أو الوقت واستيراد حزمة أدلة موقّعة وتصديرها والإعدادات وحزمة التشخيص
والقواعد. ويُضاف التحليل بالذكاء الاصطناعي اختياريًا بعد اجتياز بوابته.

**Linux:** يحتفظ بجميع المجمّعات الحالية. وتظهر الميزات التي تعتمد على النواة أو
الصلاحيات بحالة «معطّلة» مع السبب والبديل، بدل إخفائها.

**Windows:** يبدأ بدعم كامل لقراءة الأدلة وتحليلها، ثم يضيف مجمّعات جاهزة للإنتاج
للواجهات والعناوين والمسارات وجيران IP وسياسة Windows Firewall/WFP، مع التقاط
اختياري للحزم المرئية. وقد تختلف مصادر بيانات الطبقة الرابعة عن eBPF، لذلك لا
تستخدم الخطة عبارة «تكافؤ eBPF» على Windows. ويعرض التطبيق لكل حدث حقول
`source` و`capability` و`coverage` وسبب غياب أي قدرة.

## 4. البنية المستهدفة

```text
Windows APIs / Linux kernel / Npcap (اختياري) / WFP-ETW
                         │
                platform adapters  ──>  event envelope v1+
                         │                    │
                    netrewind-agent       SQLite evidence store
                         │                    │
                  local authenticated IPC / versioned API
                         │                    │
      NetRewind Desktop ─┼─ Timeline / Incident / Settings / Diagnostics
                         │
             deterministic retrieval + Isnad rules + feature extractor
                         │
                  optional local AI sidecar (no tools, no network)
```

### 4.1 إعادة تنظيم الكود قبل إضافة ميزات

1. تبقى حزم `event` و`identity` و`store` و`incident` و`correlate` نواة محايدة
   للمنصة، مع اختبارات تعاقدية لا تعتمد على نظام التشغيل.
2. تُعرّف واجهات دلالية هي `InterfaceChanges` و`AddressChanges` و`RouteChanges`
   و`NeighborChanges` و`FlowObservations` و`PolicyObservations` و`WireObservations`.
   يحول محوّل كل منصة بياناتها إلى ملاحظات مشتركة، ثم يحولها المحلل الحتمي وحده
   إلى أحداث NetRewind.
3. ينتقل إنشاء قائمة المجمّعات من `cmd/netrewindd/main.go` إلى سجل يعلن الاسم
   والمنصة والصلاحيات والتغطية والحالة وآخر نبضة وسبب التعطل. ويخضع كل محوّل جديد
   للاختبارات التعاقدية والـfixtures نفسها.
4. تُنشأ واجهة برمجية محلية ذات إصدارات (`v1`) فوق قناة اتصال محلية فقط: أنبوب
   مسمّى مع قائمة تحكم في الوصول على Windows، ومقبس Unix بصلاحيات مناسبة على Linux.
   وتصدر كائنات لنقل البيانات بدل كشف اتصال SQLite
   للواجهة. ولا تُفتح واجهة HTTP على الشبكة المحلية في الإصدار الأول.
5. تبقى أداة سطر الأوامر متوافقة، وتنتقل تدريجيًا إلى استخدام النواة والواجهة البرمجية نفسيهما. ويظل
   الاسم البديل `netrewindd` متاحًا في فترة انتقالية، من دون كسر أتمتة المستخدمين
   قبل فترة إهمال معلنة.
6. يُضاف مشغّل للترحيلات يوفر نسخة احتياطية قابلة للتحقق، وترحيلات قابلة للتكرار
   بأمان، وإصدارًا للمخطط، واسترجاعًا واختبارًا واضحًا لفتح النسخ الأحدث والأقدم.

### 4.2 الامتيازات والأمان

- الخدمة هي المكوّن الوحيد الذي يطلب صلاحيات مرتفعة؛ ولا يعمل تطبيق سطح المكتب
  بصلاحيات Administrator أو root.
- على Linux، تُحافظ الخطة على أقل مجموعة قدرات ممكنة وعلى تقوية systemd. وعلى Windows،
  تعمل الخدمة بحساب وACL مقيدين، ولا تطلب رفع الصلاحيات إلا مرة واحدة أثناء التثبيت
  أو عند تفعيل قدرة تحتاج إليه.
- تُطبّق قائمة تحكم في الوصول على دليل البيانات والمفاتيح. ويُحفظ رمز المصادقة
  باستخدام DPAPI في Windows، أو في مخزن أسرار أو ملف بصلاحيات `0600` في Linux.
  أما تشفير البيانات المخزّنة فقرار مستقل، وقد يعتمد على BitLocker أو LUKS، ولا
  يجوز ادعاء توفره قبل اختباره.
- تُعامل الحزم المستوردة بوصفها بيانات غير موثوقة؛ فيُتحقق من هجمات تجاوز مسار
  الأرشيف (`zip-slip`) والحجم والبصمات والمخطط وتاريخ المصدر. كما تُعامل أسماء DNS
  وحقول الشبكة كنصوص غير موثوقة حتى بعد تخزينها في قاعدة البيانات.
- لا تتوفر للنموذج أدوات أو سطر أوامر أو وصول إلى الملفات أو الشبكة. ولا يمر إليه
  إلا سياق تنشئه الواجهة البرمجية. ويُمنع عليه تطبيق أي إصلاح أو تغيير الشبكة تلقائيًا.

## 5. خطة التنفيذ المحكومة بالبوابات

لا تبدأ أي مرحلة قبل تسليم الشيفرة والاختبارات والأدلة والتوثيق المطلوبة للمرحلة
السابقة. ولا تحل لقطة شاشة أو عبارة «يعمل لدي» محل بوابة القبول.

### المرحلة 0 — تثبيت المتطلبات والقياس (قبل كتابة واجهة)

- أنشئ داخل `docs/product/` تعريفًا للمستخدمين المستهدفين، وحالات الاستخدام، وما يقع
  خارج النطاق، ونموذج التهديد، وسياسة البيانات، ومصفوفة دعم النظام والنواة، وخطة الترخيص.
- حدّد أقدم إصدار Windows مدعوم وتوزيعات Linux والمعماريات x64 وarm64، والأهداف
  المرجعية للذاكرة والقرص، واللغات، وسياسة العمل دون اتصال.
- حوّل سيناريوهات Linux الأربعة عشر إلى مجموعة اختبارات ثابتة تتضمن نماذج للأحداث والحوادث
  المتوقعة ومعرّفات الأدلة ولقطات الواجهة. وأضف حالات لفجوة الرصد وتوقف مجمّع ونقص
  البيانات واسم مضيف خبيث وعطلين متزامنين.
- سجّل خط أساس للأداء يشمل الأحداث في الثانية وحجم قاعدة البيانات وزمن الاستعلام
  واستهلاك الذاكرة على أجهزة مرجعية معلنة. ولا تنشر أرقامًا قبل قياسها.

**بوابة الخروج:** وثيقة متطلبات معتمدة، ومصفوفة قدرات، ومجموعة اختبارات ذات إصدار، وخط أساس
محفوظ في `docs/evidence/baselines/<version>/`.

### المرحلة 1 — عقود النواة والواجهة البرمجية وحزم الأدلة

- افصل محوّلات المنصات عن التحليل كما في §4، وأضف اختبارًا لمطابقة المخطط على Linux وWindows.
- أضف عقودًا للواجهة البرمجية وتقسيم النتائج إلى صفحات والترشيح وتدفق تحديثات الصحة وأخطاء ذات
  أنواع واضحة. وأضف المصادقة والتفويض لقناة IPC واختبارًا لعميل غير مخوّل.
- صمّم حزمة أدلة للقراءة فقط تتضمن بيان الحزمة وإصدار المخطط والتطبيق وقدرات المسجّل
  والأحداث والحوادث والقواعد ذات الصلة ومجاميع التحقق وتوقيعًا اختياريًا. ولا تتضمن
  أسرارًا أو أسماء DNS إلا بموافقة المستخدم.
- استورد الحزمة إلى قاعدة بيانات مؤقتة، ثم رقّها ذريًا بعد نجاح التحقق، من دون لمس
  السجل الأصلي عند الفشل. وأضف تصديرًا منقّحًا.

**الاختبارات:** اختبارات وحدة واختبارات خصائص ومدخلات عشوائية للحزمة، واختبارات عقود الواجهة البرمجية،
وترقية الترحيلات والتراجع عنها، والحقن وتهريب النصوص، و100 عميل قراءة متزامن،
ومقارنة نتائج أداة سطر الأوامر والواجهة البرمجية على نموذج اختبار واحد.

**بوابة الخروج:** يمكن فتح حزمة أدلة أنشئت على Linux في Windows والعكس، وتظهر
الحادثة والخط الزمني وتحذير فجوة الرصد بصورة متطابقة.

### المرحلة 2 — تطبيق سطح مكتب قابل للاستخدام قبل بدء الرصد الحي

- استخدم Tauri v2 مع React وTypeScript، واجعل وكيل Go خدمة مستقلة. يوفر هذا الخيار
  حزمة أصلية خفيفة نسبيًا من دون إعادة كتابة نواة Go. ويدعم Tauri حزم MSI أو NSIS
  على Windows، وحزم deb وrpm وAppImage على Linux.
- ابدأ بوضع **العرض التجريبي والاستيراد** فوق مجموعة اختبارات ثابتة، ثم أضف المخزن المحلي.
  ولا تربط الواجهة بقاعدة SQLite مباشرة.
- ابنِ صفحات النظرة العامة والصحة والحوادث والخط الزمني والتحقيق والقواعد وحزم الأدلة
  والإعدادات والتشخيص. وأكمل حالات الفراغ والتحميل والخطأ قبل الصقل البصري.
- أنشئ معالج تشغيل أول يتيح اختيار اللغة، ويعرض بيان الخصوصية، ويحدد مصدر الوكيل أو
  الاستيراد، ويفحص الصلاحيات والقرص والقدرات، ثم يشغّل تحقيقًا تجريبيًا بلا شبكة.

**بوابة الخروج:** يعيد اختبار شامل من البداية إلى النهاية سيناريو
`change-broke-a-path` على Windows وLinux، وينتج الحادثة نفسها، ويعرض سلسلة الأدلة،
ويلتقط صورة مرجعية لكل منصة.

### المرحلة 3 — تجربة المستخدم والتصميم البصري

النهج المقترح هو **واجهة تشغيل هادئة تبدأ بالدليل**: واضحة أثناء العطل، من دون
ألوان صارخة أو رسوم لا تساعد على اتخاذ القرار.

- شريط جانبي مختصر يضم صحة التسجيل والحوادث والخط الزمني والتحقيقات والأدلة
  والإعدادات. ويعرض أعلى الشاشة المسجّل والمضيف والنطاق الزمني وحالة الرصد.
- في صفحة الحادثة: عنوان واضح، ومستوى الثقة، وما نعرفه وما لا نعرفه، وسلسلة
  أدلة عمودية. يُعرض `causes` بخط متصل بلون تحذير، و`correlates` بخط متقطع
  محايد، و`precedes` بخط منقّط. ولا يعتمد التمييز على اللون وحده.
- في الخط الزمني: مرشحات محفوظة، وتكبير زمني، وربط الحادثة بأحداثها، ولوحة جانبية
  للدليل الخام. وعند غياب مجمّع، يظهر سبب عدم توفره بدل رسم فارغ.
- تُنظّم الإعدادات في مجموعات واضحة: **التسجيل**، **الخصوصية والبيانات**،
  **التنبيهات والتصدير**، **التحديثات**، **الذكاء المحلي**، **الدعم والتشخيص**.
  ويشرح كل إعداد أثره وقيمته الافتراضية وحساسيته، مع التحقق من صحته قبل الحفظ.
- دعم عربي كامل باتجاه RTL، مع إبقاء IP وMAC والمنافذ والطوابع الزمنية معزولة
  باتجاه LTR. ويكون تبديل اللغة فوريًا، وتبقى المصطلحات التقنية غير المترجمة مع شرح عربي عند الحاجة.
- تُضمّن الخطوط محليًا: `IBM Plex Sans Arabic` للواجهة العربية، و`Inter` أو
  `IBM Plex Sans` للنصوص اللاتينية، و`JetBrains Mono` للوقت والعناوين والحزم،
  مع `Noto Sans Arabic` وخط النظام بدائل احتياطية. وتتحقق عملية البناء من الرخص
  والأحجام والتباين.
- يدعم التطبيق السمات الفاتحة والداكنة وسمة النظام، ويلتزم WCAG 2.2 AA، ويوفر
  تنقلًا كاملًا بلوحة المفاتيح وحالات تركيز واضحة وتقليل الحركة وتكبيرًا حتى 200%،
  من دون افتراض توفر الإنترنت أو الفأرة.

**بوابة الخروج:** مراجعة تصميم لثلاثة سيناريوهات باللغتين: سجل سليم، وعطل، وفجوة
في التسجيل. ويجب ألا يرصد axe مخالفات حرجة في الإتاحة، وأن تنجح مقارنة الصور
المرجعية على العرض المعتاد ونافذة ضيقة.

### المرحلة 4 — تجهيز تطبيق Linux وخدمة التسجيل للإصدار

- غلّف وكيل Linux الحالي في خدمة رسمية تتضمن قناة الاتصال وفحوص الصحة والسجلّات
  وترحيل الإعدادات وإدارة دورة التشغيل من تطبيق سطح المكتب.
- انقل كل مجمّع قائم إلى السجل الجديد من دون تغيير دلالته، وأضف نماذج للاختبارات
  التعاقدية إلى جوار الاختبارات الحالية.
- أعد تشغيل اختبارات الوحدة والسباق والحمل، واختبارات مصدر eBPF وكائنه، ومختبر
  الأعطال الأربعة عشر، وGNS3، ثم صورة الجهاز على QEMU. ولا يكفي نجاح تطبيق سطح
  المكتب على بيانات اختبار ثابتة.
- ابنِ حزم `.deb` و`.rpm` وAppImage على أقدم خط أساس مدعوم، واختبر تثبيت كل حزمة
  وترقيتها وإزالتها وإعادة التشغيل في آلة افتراضية نظيفة. وتأكد من أن إزالة البرنامج
  لا تحذف الأدلة.

**بوابة الخروج:** يثبّت مثبّت Linux المسجّل ويشغّله بنجاح، ويقرأه تطبيق سطح المكتب
عبر القناة المحلية، وتنجح سيناريوهات المختبر الأربعة عشر والاختبار المرجعي الشامل
واختبارات الترقية والتراجع.

### المرحلة 5 — Windows: إثبات الإمكان ثم المنتج

**5A: تجربة معزولة، لا تدمجها مبكرًا.** اختبر واجهات Windows IP Helper لتغيّر
الواجهات والعناوين والمسارات والجيران، وWFP/ETW للسياسات والاتصالات المحظورة.
ولا تستخدم Npcap إلا إذا كان التقاط DHCP وDNS وICMP ضروريًا ومسموحًا قانونيًا.
يؤكد توثيق Microsoft توفر إشعارات الواجهات والمسارات وعناوين البث الأحادي، لكنه لا
يجعلها مكافئة لـnetlink تلقائيًا. لذلك يجب اختبار الفقد والاستدعاءات الراجعة وIPv4 وIPv6
والسكون والاستئناف وVPN.

**5B: محوّل جاهز للإنتاج.** لا يبدأ إلا بعد نجاح التجربة المعزولة:

- يقرأ `windows.netio` الحالة الأولية ثم الإشعارات، ويحوّلها إلى الملاحظات والأحداث
  نفسها التي ينتجها Linux، مع إرفاق الدليل الخام المناسب.
- يسجّل `windows.wfp` تغيّرات السياسات والأحداث المحظورة بحجم منخفض افتراضيًا. ولا
  يُفعّل تدقيق الاتصالات الناجحة افتراضيًا، لأن Microsoft تحذر من الحجم الكبير الذي
  قد ينتج عنه. ولا تُبنَ `first_failure_for_pair` إلا بعد إثبات وجود مصدر محدود وآمن.
- تكون قدرة `windows.wire` اختيارية، وترتبط بتوفر Npcap واختيار محوّل الشبكة وسياسة
  الخصوصية. وعند غيابها، يسجّل التطبيق السبب بوضوح ولا يوهم المستخدم بأنه يراقب
  حركة البث.
- صمّم مثبّت خدمة Windows وآلية الاستعادة ومصدر سجل الأحداث وقوائم التحكم في الوصول
  والتنظيف ومجمّع التشخيص. وافصل توقيع الملف التنفيذي عن ترخيص برنامج التشغيل وتوقيعه.

**اختبارات Windows:** VMs نظيفة لكل إصدار مدعوم، IPv4/IPv6، Wi-Fi/Ethernet/VPN، sleep/resume، reboot/upgrade، user بلا Admin، تلف DB، packet-loss/backpressure، adapter disabled، firewall change، واستيراد Linux evidence. تجرى تغييرات الشبكة فقط داخل VM معزولة ثم تستعاد snapshot.

**بوابة الخروج:** يكون تقرير القدرات صحيحًا في جميع الحالات، ولا يحدث فقد صامت
للبيانات، وتنجح نماذج الاختبار الدلالية المشتركة. وتظل أي ميزة لم تبلغ عتبة الإثبات
«تجريبية» أو «معطّلة»، ولا تدخل ضمن ادعاءات الإصدار العام.

### المرحلة 6 — الذكاء المحلي (بعد المنتج الحتمي)

#### الاختيار المبدئي

نقطة البداية المعقولة هي **Qwen3-4B Instruct بصيغة GGUF المكمّمة `Q4_K_M` عبر
llama.cpp**. لا يعني ذلك أنه «أفضل نموذج» نظريًا، بل إنه فرضية أولى قابلة للقياس:

- Qwen3-4B مرخص بموجب Apache-2.0، ويحتوي على أربعة مليارات معلمة، ويدعم أكثر
  من مئة لغة، وتبلغ نافذة سياقه الأصلية 32K. كما يتيح نمطًا للتفكير المتعمق وآخر
  للاستجابة الأسرع.
- تناسب صيغة GGUF ومحرك llama.cpp المعالجات المركزية؛ إذ تدعم مستويات تكميم من
  1.5 إلى 8 بت، وتشغيلًا محليًا على Windows وLinux من دون اشتراط معالج رسومي.
  ويجب تثبيت إصدار المحرك وبنيته ومستوى التكميم، وعدم تنزيل نسخة غير محددة الإصدار.
- يستخدم الملف المتوازن Q4_K_M مع نافذة سياق محدودة افتراضيًا بين 4K و8K، ويُحدد
  عدد مسارات التنفيذ بعد القياس. أما الأجهزة محدودة الموارد فتستخدم Qwen3-1.7B
  أو نموذجًا آخر يجتاز الاختبار، ولا تُجبر على تشغيل نموذج 4B بذاكرة غير كافية.
  ويمكن للأجهزة الأقوى استخدام نموذج 8B بعد قياس واضح.
- **Gemma 3 4B** مرشح للمقارنة، وليس بديلًا محسومًا. تصفه Google بأنه مناسب
  لأجهزة سطح المكتب والخوادم الصغيرة، وينتمي إلى عائلة متعددة اللغات. ويخضع
  للاختبارات ومراجعة الترخيص نفسيهما قبل عرضه للمستخدم.

لا تكفي صيغة الملف أو حجمه أو استهلاك الذاكرة للحكم على الجودة. ولا يُختار
Phi أو Gemma أو Qwen بناءً على اختبار عام أو شهرة الاسم؛ فمجموعة الاختبار
الشبكية ثنائية اللغة هي المرجع. ولا تُشحن أوزان نموذج قبل نجاح إصدار محدد في
التقييم واكتمال مراجعة الترخيص والمصدر.

#### تصميم آمن للذكاء الاصطناعي

1. **استرجاع حتمي للبيانات:** يستدعي API سلسلة الحادثة والأحداث القريبة وقدرات
   المجمّعات وفجواتها والقواعد المطابقة وإحصاءات بسيطة. يبدأ بـSQLite FTS واسترجاع
   القواعد، ويؤجل نموذج التضمين إلى مرحلة مستقلة.
2. **توجيه قصير ومغلق:** يمرر الحقائق مع معرّفات الأحداث وحقل `unknowns`، ويلزم
   النموذج بألا يخترع حدثًا أو يتجاوز ثقة الدليل أو يقترح تنفيذ تغيير. كما يرفض
   الاستنتاج عند وجود فجوة أو توقف مجمّع.
3. **مخرجات مقيدة بمخطط JSON:** تشمل `summary` و`ranked_hypotheses[]`
   و`evidence_event_ids[]` و`counter_evidence[]` و`unknowns[]`
   و`confidence_ceiling` و`next_checks[]`. تتحقق الخلفية من المعرّفات وسقف الثقة
   قبل العرض. وإذا كانت JSON غير صالحة، تُعاد المحاولة مرة واحدة ثم تظهر رسالة فشل آمنة.
4. **واجهة واضحة:** تعرض وسم «فرضية مولّدة بالذكاء الاصطناعي، وليست دليلًا» وروابط لكل معرّف وزرًا
   للمقارنة مع الحادثة الحتمية وخيار نسخ التقرير وحذف النموذج والبيانات أو تعطيلهما.
   ولا ترسل أي بيانات خارج الجهاز.
5. **مدير للنموذج:** يستخدم بيانًا موقّعًا يستضيفه المشروع، وعنوان URL ثابتًا،
   وSHA-256 وتوقيعًا منفصلًا وTLS. كما يدعم الاستئناف الآمن وقياس القرص والذاكرة
   قبل التنزيل والإيقاف المؤقت والإلغاء والحذف والاختبار الذاتي ومجلد عزل للملفات
   التالفة. ولا ينزّل ملف GGUF عشوائيًا من مصدر مجتمعي في بيئة الإنتاج.

#### بوابة اختيار النموذج

أنشئ `ai/eval/` قبل واجهة الذكاء الاصطناعي: أربعة عشر سيناريو من المختبر، وحوادث
منزوعة الهوية، وحالات سلبية وملتبسة، وصياغات عربية وإنجليزية، ومحاولات لحقن
التعليمات داخل أسماء DNS والمضيفين. افصل مجموعات التدريب والتطوير والاختبار، ولا
تضف الاختبار المخفي إلى المطالبة نفسها.

لكل مرشح/quantization/platform سجّل: الإصدار، hash، الرخصة، hardware، RAM peak، tokens/sec، p50/p95، حرارة/استهلاك إن أمكن، JSON-validity، citation precision، Top-1/Top-3 cause coverage، false-causality، نجاح refusal عند gap، والنص العربي.

**معايير منع الإصدار، وتُحدد قيمها النهائية بعد قياس خط الأساس:** يجب أن تكون
JSON ومعرّفات الأحداث صحيحة بنسبة 100%، وألا يظهر ادعاء سببي عند وجود فجوة أو
توقف مجمّع، وألا تتوفر للنموذج أدوات أو شبكة أو أوامر، وألا يتجاوز ميزانية الذاكرة
وزمن الاستجابة المعلنة. ولا ينتقل أي مرشح إلى النسخة التجريبية قبل تحقيق عتبة
Top-3 ودقة الاستشهاد المتفق عليهما على مجموعة اختبار مجمدة، واجتياز الاختبارات
الهجومية. وتعني النتيجة الضعيفة إبقاء الذكاء الاصطناعي معطلًا، لا خفض العتبة بصمت.

### المرحلة 7 — تهيئة المنتج للإصدار والنسخة التجريبية

- سلسلة التوريد: بيانات إصدار قابلة لإعادة الإنتاج، وقائمة مكونات بصيغتي SPDX أو

  وتجريبية، ومفاتيح ميزات محلية لا تخفي نقص التغطية.
- قبل الإصدار العام: مراجعة أمنية مستقلة، ومراجعة AGPL-3.0 وحقوق العلامة وتراخيص
  مكونات Go وRust وNode وNpcap والخطوط والنماذج، وإشعار خصوصية، واتفاقية استخدام
  عند الحاجة، وسياسة دعم، وقائمة ظاهرة بالقيود المعروفة.

## 6. منهج عمل إلزامي لأي مطوّر أو وكيل

لا تبدأ المهمة بتعديل عشوائي للشيفرة. تمر كل مهمة بالمراحل التالية، وتوثّق نتائجها
في طلب التغيير:

1. **الاستكشاف:** اقرأ ملفات المعمارية والمخطط والقواعد والاختبارات ذات الصلة، وحدد
   الأطراف المتأثرة، واكتب متطلبًا قابلًا للاختبار وما يقع خارج النطاق ومخاطر المنصة.
2. **التصميم قبل التنفيذ:** اكتب ADR مختصرًا يوضح البدائل وسبب الاختيار والعقود
   والترحيل والخصوصية والأمان والقياس عن بُعد وأنماط الفشل والتراجع. ويحتاج أي تغيير
   دلالي في الحدث إلى fixture وقرار واضح للمخطط.
3. **الاختبار أولًا أو بالتوازي:** أضف اختبارات وحدة للمنطق، واختبارات تعاقدية
   للمحوّل، وحالات سلبية وهجومية، وتكاملًا مع المخزن وAPI، واختبار E2E لمسار المستخدم.
   وأضف حالة إعادة إنتاج صغيرة لكل عطل.
4. **تنفيذ صغير قابل للمراجعة:** لا تخلط إعادة هيكلة واسعة بميزة جديدة، ولا تضف
   بيانات اعتماد أو صلاحيات واسعة، ولا تغيّر مسارات أو أوامر الإنتاج بلا تصميم وتأكيد.
5. **الإثبات:** سجّل الأمر وإصدار النظام ونتائج الاختبار وسجلّات الفشل، وأرفق قاعدة
   أو حزمة محدودة ولقطة شاشة أو فيديو قصير للحالة النهائية على Windows وLinux، ودليل
   الإتاحة عند تغيير الواجهة. استخدم مسارات مثل
   `docs/evidence/<release>/<os>/<scenario>/` واربط الملفات بالالتزام وبصمة التحقق.
6. **التوثيق والتسليم:** حدّث مساعدة المستخدم والقيم الافتراضية والصلاحيات والقيود
   واستكشاف الأخطاء وملاحظات الإصدار وخطوات الترحيل والتراجع. ولا تُدمج المهمة إذا
   ادعت الوثائق شيئًا لا تثبته الاختبارات.

### شروط اكتمال الإصدار

- ترتبط كل قدرة مذكورة في التسويق أو التوثيق باختبار ونظام تشغيل وصلاحية مطلوبة.
  وما لا يملك اختبارًا يوصف بأنه تجريبي أو غير مدعوم.
- لا تخفي أي حادثة أو إجابة مولّدة بالذكاء الاصطناعي فجوة في التسجيل أو مصدرًا
  مفقودًا؛ وتعرض واجهة المستخدم هذا النقص قبل أي استنتاج.
- يجتاز Windows وLinux مجموعة الاختبارات المشتركة، ويصدران تقريرين قابلين للمقارنة،
  مع توثيق الفروق في مصفوفة القدرات.
- تُختبر عمليات التثبيت والترقية والإصلاح والإزالة والتراجع في جهاز افتراضي نظيف،
  ولا تحذف البيانات أو الإعدادات من دون اختيار صريح.
- تكون جميع الملفات الناتجة موقّعة ومتحققًا منها، ويتوفر SBOM، وتخضع الحزم للفحص الأمني.
- يكتمل دليلا المستخدم العربي والإنجليزي، وتُلتقط صور حقيقية من النسختين، وتُكتب
  القيود المعروفة قبل الإصدار العام.

   الأساس. **لا يبدأ الذكاء الاصطناعي أو التقاط Windows قبل اكتمالها.**
3. تنفيذ المرحلة 1، ثم وضعي الاستيراد والعرض التجريبي في تطبيق سطح المكتب، لتقديم
   قيمة مبكرة على Windows وLinux من دون ادعاء وجود التقاط غير منفّذ.
4. إبقاء بوابة منع التراجع على Linux فعّالة أثناء تجهيز المنتج، ثم تنفيذ تجربة
   Windows بمعزل عن الإصدار العام إلى أن تثبت صلاحيتها.
5. جمع مجموعة بيانات واقعية من البرنامج التجريبي، بموافقة واضحة ومن دون أسرار، ثم
   قياس Qwen وGemma ومستويات التكميم، واختيار إصدار ثابت بناءً على نتيجة منشورة.
6. تشغيل البرنامج التجريبي بمصفوفة دعم صادقة، ثم طرح الإصدار العام بعد اجتياز
   بوابات المرحلة 7 فقط.
